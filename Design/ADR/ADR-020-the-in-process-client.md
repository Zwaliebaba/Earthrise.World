# ADR-020 — The in-process client: state updates, queries and the clock

**Status:** Proposed, 2026-11-01, with the M3 plan ([MvpPlan.md](../MvpPlan.md), M3; [MvpPlan-M3.md](../MvpPlan-M3.md)). It fixes how the first client joins the simulation in one process, which [ADR-002](ADR-002-authoritative-simulation.md), decision 3, describes and leaves to the time the client is built; it sets the first queries and their budget, which [ADR-009](ADR-009-queries-across-the-server-boundary.md) leaves to M3; and it amends [ADR-010](ADR-010-solution-and-build-layout.md), decision 2: `Client` and `Earthrise` both join the solution in M3. The owner gave it the go-ahead on 2026-11-01, as written, with ADR-010's amendment (MvpPlan.md, M3, input 1; GameDesign.md, *M3's values*, item 1). Order M3-C1 implements the projects and marks it Accepted; M3-B2 and M3-B3 implement the state update and the queries, and M3-C3 the clock (AGENTS.md §6).

## Context

- **ADR-002 settles the shape:** the simulation owns the world, only messages cross the boundary, commands are bytes from the first line, and in single-player state updates cross as value copies, never as a pointer or reference into simulation state. Chunks cross as the copy-on-write snapshots M1 built. The client project cannot include the simulation's headers (decision 3). What a state update holds, and how often one crosses, is left to the client that first needs it.
- **ADR-009 adds queries and answers,** read-only, answered on the tick's state after its own work within a budget counted in units of work, oldest dropped first, as bytes through the same transport as commands. It leaves open which queries exist beyond Hud.md's list and how many a tick answers, "set in M3 when the first queries exist".
- **ADR-013 fixes the clock:** 20 ticks a second, wall time meets ticks at one seam outside the simulation, a fixed-step accumulator in the executable, and a tick is never skipped, merged or shortened: when a machine cannot keep up, game time slows. The client's interpolation between ticks is left open.
- **ADR-010 says `Client` and `Earthrise` join "when M3 and M4 need them"**, and [ADR-016](ADR-016-server-data-format.md), decision 7, has `Earthrise` compare the two shared hashes "from M4". M3 is the first milestone with a client, and it needs the executable that joins the client to the simulation: the window, the device, the build id ([ADR-014](ADR-014-edits-saves-and-replays.md), decision 6), the shared-hash check and the clock. Writing those into a throwaway executable and moving them in M4 would be work done twice.
- **M2's `World`** publishes chunk snapshots (`Publish`) and exposes its entities to the tests and the bench as `const std::map` references. A client may not hold those references (ADR-002). Its tick has two empty steps for M3 to fill: `PublishState` and `AnswerQueries`.
- **The renderer spike holds the client's drawing code** (`RendererSpike/WorldView`, `Debris`), written against snapshots and `Content`, and it must stay as a benchmark (MvpPlan.md, *Solution layout*).
- **M3's breach lab** needs three things only the simulation can answer (Hud.md §8 and §10; GameDescription.md, *Readability*): whether a shot can be fired at a point and what it would strike; a wall section's integrity reading, from the resolver ([ADR-004](ADR-004-rule-based-destruction.md), decision 5); and where foot soldiers can reach, from navigation ([ADR-015](ADR-015-navigation.md), *Consequences*). It also needs to run the automatic parts of a prediction item faster than real time, and to pause while a question is up.

## Decision

1. **`Client` and `Earthrise` join the solution in M3** (ADR-010, decision 2, amended on acceptance). `Client` is a static library on `Core`, `Engine`, `Protocol` and `Content`, and never `Simulation`. `Earthrise` is the Windows executable on every library; in M3 it runs the breach lab, and M4 adds the Siege trial to it. `RendererSpike` gains a reference to `Client`, because the world view and the debris move there from the spike. `Build/CheckProjectFiles.py` gains the table of which project may reference which, so that the boundary of ADR-002 holds by check and not by discipline.
2. **The transport is two queues of bytes and one copy a tick, in `Earthrise`.** Each tick the executable hands the simulation the client's queued command bytes (`World::Submit`) and query bytes (`World::Ask`), ticks it, and hands the client a copy of the simulation's state update (`World::State`), the chunks it published (`World::Publish`) and the answers it produced (`World::TakeAnswers`). The client, `Client::Session`, keeps its own copy of all of it and draws from nothing else. No pointer or reference crosses in either direction; the chunk snapshots are the one sanctioned shared handle (ADR-002, decision 3).
3. **A state update is a value, the whole visible state, once a tick.** `Protocol::StateUpdate` holds the tick and every entity the client may see, each as a view: structures (template, origin, turn and name), siege engines (kind, cell, facing and reload), squads, units (kind, position and cell), shots (position) and collapses in progress (the piece, its strip, the ticks left of its warning and its fall, and, once it falls, the voxels that fell and the rubble they became), with the tick's shot hits. Everything is in id order. In M3 it crosses as a struct copy and has no byte encoding; it gains one, with a record version, when online work starts (ADR-002, decision 3). It is filtered by what the player can see, through one seam, `World::PublishState(player)`; in M3 there is one player and no fog, so the filter passes everything, and M4's fog filter goes into that seam.
4. **The clock is a fixed-step accumulator in the client, fed by the executable.** `Client::TickClock` takes wall seconds times a speed and gives the ticks due, at most eight a frame; what is left over waits, so a slow machine slows game time and never skips a tick (ADR-013, decision 2). It can be paused. The speed is the breach lab's fast-forward, 10× during a prediction item's automatic parts (MvpPlan.md, M3, input 4); it changes how many ticks a frame runs and nothing inside a tick. In M3 nothing is interpolated: an entity is drawn where its last state update put it. At 20 ticks a second a walking figure moves about 7 cm a tick, about one screen pixel at the default zoom, so this is judged on screen in M3 and interpolation stays open.
5. **M3's queries are three,** each a tagged record with a version, as commands are (ADR-002, decision 3), and each answered by a reading that carries the query's id and the tick it was computed on (ADR-009, decision 3):
   - **An aim check:** an engine and a target voxel. The reading is Hud.md §8's: IN RANGE, BLOCKED, TOO CLOSE or OUT OF RANGE, the distance across the ground in whole metres, and the voxel the shot would strike, traced along the shot's own arc through the voxel grid, so that the cursor shows where the shot will land. A shot that strikes the target or one of its six face neighbours is IN RANGE; one that strikes anything else first is BLOCKED.
   - **A section's integrity:** a structure. The reading is the integrity view's (ADR-021; GameDescription.md, *Readability*), computed by the resolver's own search and never by a copy of its rule.
   - **Reach in a tile:** a navigation class, a start cell and a tile. The reading is two bitsets of the tile's 1,024 cells: which the class can enter, and which it can reach from the start, from navigation's per-tile components (ADR-015, M2-F4), the same answer the squads move by.
6. **Queries are budgeted in units of work, in `RULE`,** as ADR-009 and ADR-013 require: `queryWorkPerTick`, Proposed at 16, with each kind's cost fixed: an aim check 1, a tile's reach 1, a section's integrity 8, the most support searches it runs. Step 12 answers the oldest queries first until the budget is spent; a query that does not fit waits for the next tick; past `MAX_PENDING_QUERIES`, 64, the oldest is dropped. A malformed query throws in step 12 as a malformed command does in step 1. The client keeps the newest answer for each thing it asks about and asks again when the pointer moves or the world changes, so a dropped or waiting query costs staleness, never a wrong reading (ADR-009, decision 5). Answers pass the same filter as the state update; in M3 it passes everything.
7. **`Earthrise` computes its build id from its own file at startup** (ADR-014, decision 6) and refuses to start when `ServerData`'s shared hash differs from `Content`'s (ADR-016, decision 7), from M3 rather than M4.

## Consequences for the code

- **`Protocol` gains** `StateUpdate` and its views, `Query`, `Answer` and their encoders, and the enumerations the views need, `EngineKind`, `UnitKind` and `NavigationClass`, which move out of `Simulation`, as does `FixedPosition`. `Simulation` keeps using them under its own namespace through using-declarations, so nothing else in it changes.
- **`Simulation::World` gains** `State`, `Ask`, `TakeAnswers` and `Quiet`, which says whether anything is in flight, for the lab's fast-forward to stop on; `PublishState` and `AnswerQueries` fill in; `Rules` gains `queryWorkPerTick`.
- **`Client` gains** `Session`, `TickClock` and the world view and debris from the spike, over `Protocol` types.
- **`Earthrise`** is the one place that holds both a `Simulation::World` and a `Client::Session`.
- **A test** in `SimulationTests` checks each query's budget, order and dropping, and `ProtocolTests` round-trips each query and each answer, as `CommandTests` does for commands.

## What this forecloses

- The client reading simulation state through anything but a state update, a snapshot or an answer.
- A state update that carries less than the whole visible state, until a measured need and online work's byte encoding.
- A query that costs more than the whole budget, or one whose cost is not fixed in advance.
- A speed-up that shortens or merges ticks: fast-forward runs more ticks, never different ones.

## Left open

- Interpolation between ticks (ADR-002, ADR-013), judged in M3 on screen and decided in M4 if units stutter.
- The byte encoding of state updates, and deltas in place of the whole state, with online work.
- Which queries M4 and M6 add: the placement and dig readouts (Hud.md §10), and the what-if of a dig.
- Whether a client over a network keeps the same whole-state update, or a delta.
